# Reclaw Specification

Status: Implementation contract
Last updated: 2026-03-06
Scope: `packages/plugin` + `packages/skill`

## 1. Identity

- Product name: `Reclaw`
- Plugin id: `reclaw`
- Skill package: `@reclaw/skill`
- Plugin kind: `memory`
- Default store directory: `~/.openclaw/reclaw`
- Nightly snapshot cron: `reclaw-memory-snapshot`
- Import worker cron prefix: `reclaw-import-worker-`

Managed marker families used by the plugin:

- `<!-- BEGIN/END RECLAW MEMORY SNAPSHOT -->`
- `<!-- BEGIN/END RECLAW SESSION HANDOFF -->`
- `<!-- BEGIN/END RECLAW MEMORY GUIDANCE -->`
- `<!-- BEGIN/END RECLAW MEMORY NOTICE -->`

## 2. Overview

Reclaw is an OpenClaw memory-slot plugin that replaces `memory-core`.

It provides a durable memory system built from four pieces:

1. An append-only structured event log in `log.jsonl`
2. A subject registry in `subjects.json`
3. A state file in `state.json`
4. Wrapped `memory_search` / `memory_get` tools plus derived markdown surfaces (`MEMORY.md` blocks and subject projections)

The log is the source of truth. `MEMORY.md` is a derived cache that keeps the most useful current context in prompt-ready form.

Reclaw does not use legacy daily memory files such as `memory/YYYY-MM-DD.md`.

## 3. Core Contracts

- Reclaw is the active memory system when installed and initialized. It occupies `plugins.slots.memory = "reclaw"`.
- Durable memory is stored as structured events, not prose notes.
- Event writes are append-only during normal extraction and import. Corrections are represented as newer events, not in-place edits.
- The only routine log rewrite supported by the implementation is administrative subject renaming, which rewrites `subject` values across the log.
- `MEMORY.md` remains important because OpenClaw auto-loads it into sessions. Reclaw uses it for:
  - user-maintained manual context
  - a nightly generated memory snapshot block
  - a latest-session handoff block
- Reclaw also maintains per-subject markdown projection files under the workspace so builtin markdown indexing can semantically search event-log content.
- The event log is authoritative when `MEMORY.md` and the log disagree.
- Semantic search applies to indexed markdown memory content surfaced through the builtin memory tool integration. Reclaw bridges event-log content into that leg through generated per-subject markdown projections; the raw `jsonl` log itself is still searched with structured filters and keyword matching, not a vector index.
- Extraction only stores user-specific, durable information. Generic world knowledge and one-off browsing artifacts are filtered out.
- Main-session traffic is the normal extraction scope. By default, session keys prefixed with `cron:`, `sub:`, or `hook:` are skipped.

## 4. Configuration

Reclaw's runtime config shape is:

```json
{
  "logDir": "~/.openclaw/reclaw",
  "extraction": {
    "model": "anthropic/claude-sonnet-4-6",
    "skipSessionTypes": ["cron:", "sub:", "hook:"]
  },
  "briefing": {
    "model": "anthropic/claude-sonnet-4-6",
    "activeWindow": 14,
    "staleThreshold": 30,
    "maxLines": 120
  },
  "cron": {
    "schedule": "0 3 * * *",
    "timezone": "America/New_York"
  }
}
```

Notes:

- `cron.timezone` defaults to the local machine timezone when unset.
- OpenClaw's existing `agents.defaults.memorySearch` settings remain the search/embedding config used by the builtin markdown search leg.

## 5. On-Disk Layout

Reclaw's persistent store lives in one directory:

```text
~/.openclaw/reclaw/
  log.jsonl
  subjects.json
  state.json
```

Related provenance data lives in OpenClaw's transcript store:

```text
~/.openclaw/agents/<agentId>/sessions/<sessionId>.jsonl
```

For imported history, Reclaw can also write OpenClaw transcript sessions under `~/.openclaw/agents/<agentId>/sessions/`. The default imported agent id is `main`.

Workspace-visible derived markdown used for builtin semantic search lives under:

```text
<workspace>/
  MEMORY.md
  reclaw-memory/
    subjects/
      <subject-slug>.md
```

## 6. Data Schemas

### 6.1 Event log

`log.jsonl` is a newline-delimited sequence of structured events.

Supported event types:

| Type | Purpose |
|---|---|
| `task` | Actionable work with `status: "open" | "done"` |
| `fact` | Learned or observed user-specific information |
| `decision` | A choice or commitment, usually with reasoning in `detail` |
| `question` | An unresolved user-relevant open loop |
| `handoff` | Session-boundary working state summary |

Common fields:

| Field | Required | Notes |
|---|---|---|
| `id` | yes | 12-character nanoid generated by the system |
| `timestamp` | yes | ISO 8601 string |
| `type` | yes | One of the event types above |
| `content` | yes | Main event text |
| `session` | yes | OpenClaw session id for provenance |
| `detail` | no | Supplemental context |
| `subject` | yes for non-handoff | Canonical subject slug; missing live/import output is normalized to `unknown` for non-handoff entries |
| `status` | yes for task | `open` or `done` |

Contracts:

- Live extraction does not let the model supply `id`, `timestamp`, or `session`; the system injects them.
- Historical import may preserve per-entry timestamps when valid; otherwise it falls back to the conversation's `updatedAt`.
- Live extraction enforces exactly one final `handoff` event. If the first model output violates that contract, Reclaw runs a repair pass; if repair still fails, the extraction run fails.
- Corrections are represented as later events on the same subject. There is no `replaces` linkage field.

Examples:

```jsonl
{"timestamp":"2026-02-20T14:20:00.000Z","id":"a3k9x_BmQ2yT","type":"decision","subject":"auth-migration","content":"Queue-based retries for webhook delivery instead of synchronous retries","detail":"Synchronous retries amplified failures during the outage","session":"abc12345"}
{"timestamp":"2026-02-20T14:35:00.000Z","id":"r7Wp3nKx_mZe","type":"fact","subject":"auth-migration","content":"Exponential backoff currently uses 1s, 5s, and 15s retry intervals","session":"abc12345"}
{"timestamp":"2026-02-20T15:10:00.000Z","id":"Ht4vL_9qRx2D","type":"task","status":"open","subject":"auth-migration","content":"Write the backfill script for failed webhook jobs","session":"abc12345"}
{"timestamp":"2026-02-20T15:30:00.000Z","id":"Ym8kP_3wNx5Q","type":"handoff","subject":"auth-migration","content":"Retry logic is implemented; backfill and canary remain","detail":"Backfill script is not started and load testing is still pending","session":"abc12345"}
```

### 6.2 Subject registry

`subjects.json` is a JSON object keyed by slug:

```json
{
  "auth-migration": { "display": "Auth Migration", "type": "project" },
  "alice-chen": { "display": "Alice Chen", "type": "person" }
}
```

Subject contract:

- Slugs are lowercase kebab-case.
- Valid subject types are `project`, `person`, `system`, and `topic`.
- `topic` is the fallback type when no valid type hint is available.
- Extraction can auto-create new subjects and can update an existing subject's type when a valid `subjectType` hint is returned.
- CLI subject rename updates both `subjects.json` and historical `subject` values in `log.jsonl`.

### 6.3 Subject markdown projections

Reclaw maintains one generated markdown file per subject at:

```text
<workspace>/reclaw-memory/subjects/<slug>.md
```

Projection contract:

- Projection files are derived from `log.jsonl` plus `subjects.json`; they are not a second source of truth.
- Files are workspace-visible markdown specifically so OpenClaw's builtin markdown indexer can semantically search event-log content.
- Manual edits to projection files are not preserved. Refresh rewrites the full file.
- Projection refresh is best-effort. Projection write failures do not roll back successful log extraction/import writes.
- A projection file may exist for a registry subject even when it has no events yet.

Each file should contain:

- the subject display name, slug, and subject type
- a generated-at timestamp
- a section for currently open items for that subject
- a chronological event timeline with event ids preserved in the markdown

Minimal shape:

```markdown
# Auth Migration

- Subject: `auth-migration`
- Type: `project`
- Generated: `2026-03-06T12:00:00.000Z`

## Open Items

- [task/open] Write the backfill script (`Ht4vL_9qRx2D`)

## Timeline

- 2026-02-20T14:20:00.000Z [decision] Queue-based retries for webhook delivery instead of synchronous retries (`a3k9x_BmQ2yT`)
- 2026-02-20T15:10:00.000Z [task/open] Write the backfill script for failed webhook jobs (`Ht4vL_9qRx2D`)
```

Refresh triggers:

- after successful live extraction, regenerate the projections for all touched subjects
- after successful non-dry-run import, refresh the full subject projection set
- after subject add/rename operations, refresh the affected subject projections
- on demand through CLI refresh commands

### 6.4 State file

`state.json` stores operational state in addition to memory content:

```json
{
  "extractedSessions": {
    "abc12345": {
      "at": "2026-02-20T15:30:00.000Z",
      "entries": 7,
      "lastMessageAt": "2026-02-20T15:29:00.000Z",
      "sourceSessionKey": "agent:main",
      "workerSessionId": "worker-1",
      "workerSessionKey": "isolated:worker-1"
    }
  },
  "failedSessions": {},
  "importedConversations": {
    "chatgpt:conv-123": {
      "at": "2026-02-22T09:10:00.000Z",
      "updatedAt": "2026-02-20T14:20:00.000Z",
      "sessionId": "reclaw:chatgpt:conv-123",
      "entries": 12,
      "title": "Webhook retry planning"
    }
  },
  "eventUsage": {
    "r7Wp3nKx_mZe": {
      "memoryGetCount": 4,
      "memorySearchCount": 9,
      "citationCount": 2,
      "lastAccessAt": "2026-03-01T18:22:11.000Z"
    }
  },
  "importJobs": {
    "job-1": {
      "status": "queued",
      "platform": "chatgpt",
      "filePath": "/tmp/export.json",
      "options": {},
      "createdAt": "2026-03-01T10:00:00.000Z",
      "updatedAt": "2026-03-01T10:00:00.000Z",
      "queuedAt": "2026-03-01T10:00:00.000Z",
      "attempts": 0
    }
  },
  "compactionSessions": {
    "abc12345": {
      "at": "2026-03-01T10:30:00.000Z",
      "messageCount": 42,
      "compactedCount": 18,
      "status": "observed"
    }
  },
  "snapshotRuns": [
    {
      "at": "2026-03-01T03:00:00.000Z",
      "status": "success",
      "memoryMdPath": "/workspace/MEMORY.md"
    }
  ]
}
```

State responsibilities:

- `extractedSessions`: latest successful extraction watermark per session (`lastMessageAt` plus transcript message count)
- `failedSessions`: retry tracking for failed extraction runs, keyed to the same watermark concept
- `importedConversations`: import dedupe by `<platform>:<conversationId>`
- `eventUsage`: usage signals used by snapshot selection
- `importJobs`: async import queue state
- `compactionSessions`: observed compaction activity and delta-extraction outcome
- `snapshotRuns`: recent snapshot generation outcomes

Usage scoring for durable snapshot selection is:

```text
2 * citationCount + memoryGetCount + 0.25 * memorySearchCount
```

## 7. Extraction and Session Lifecycle

### 7.1 Extraction triggers

Reclaw registers these lifecycle hooks:

- `session_end`: primary full-session extraction path
- `before_reset`: extraction before reset/new-session flows, using inline messages when available
- `before_compaction`: preferred pre-compaction delta-extraction path when the runtime emits it
- `after_compaction`: delta extraction for new transcript content after compaction
- `gateway_start`: startup sweep for unextracted or failed sessions

Scope rules:

- Sessions are eligible when their session key looks like a main session: `agent:<agentId>:main...`, `agent:<agentId>`, or `dm:...`
- Sessions with keys starting `cron:`, `sub:`, or `hook:` are skipped by default

### 7.2 Transcript sources

By trigger:

- `session_end`: reads the session transcript file
- `before_reset`: prefers inline `messages[]`, then `sessionFile`, then transcript lookup by `(agentId, sessionId)`
- `before_compaction`: prefers inline `messages[]`, then `sessionFile`, then transcript lookup by `(agentId, sessionId)`
- `after_compaction`: uses the compaction event's `sessionFile` when possible, otherwise resolves the session and transcript by context or fallback discovery
- `gateway_start`: scans known transcript sessions at startup

Transcript provenance is retained through the event `session` field, and `memory_get("session:<id>")` can be used to read the underlying conversation when the transcript can be resolved.

### 7.3 Extraction prompt context

Each extraction run supplies the model with:

- the known subject registry
- relevant existing entries for mentioned subjects
- currently open tasks and questions
- the current transcript

Existing subject history is capped per subject to keep prompt size bounded.

### 7.4 Dedupe and retry behavior

- Extraction state is watermark-based, not simply "this session ran once already".
- A later extraction for the same session id is allowed when the transcript has moved forward beyond the most recent successful or failed extraction watermark.
- `before_compaction` and `after_compaction` are delta-oriented paths for long-running sessions that keep the same session id across compactions.
- Failed extraction attempts are retried once for a given watermark. Newer transcript content may trigger a later extraction attempt.
- State entries older than 30 days are pruned from extraction, failure, compaction, and snapshot-run bookkeeping.

### 7.5 Transcript citations

When the transcript contains prior event references in the form `[<12-char-id>]`, Reclaw increments `citationCount` for those referenced events if they exist in the log.

### 7.6 Live handoff enforcement

Live extraction has a stricter handoff contract than import:

- exactly one `handoff` event must be present
- that handoff must be the final emitted event

If the first model output violates that contract, Reclaw runs a repair pass and asks the model to fix the extraction output. If repair still does not produce exactly one final handoff, the extraction run fails rather than silently persisting malformed live output.

## 8. MEMORY.md Contract

`MEMORY.md` remains the prompt-friendly memory surface.

The implementation treats it as:

- a manual section maintained by the user or workspace
- a generated snapshot block managed by Reclaw
- a latest handoff block managed by Reclaw
- optionally, a managed notice block inserted via the post-init guidance flow

### 8.1 Managed blocks

Reclaw owns these blocks:

```markdown
<!-- BEGIN RECLAW MEMORY SNAPSHOT -->
... generated snapshot ...
<!-- END RECLAW MEMORY SNAPSHOT -->

<!-- BEGIN RECLAW SESSION HANDOFF -->
... latest handoff ...
<!-- END RECLAW SESSION HANDOFF -->
```

The snapshot writer only edits the snapshot block. The handoff writer only edits the handoff block.

If the markers are missing, Reclaw appends them and writes the generated content between them.

### 8.2 Session handoff block

When a new handoff event is written, Reclaw rewrites the handoff block using the latest emitted handoff from that run.

Current formatting contract:

```markdown
## Previous Session Handoff (agent:agent-1:main:session-h2)

Auth migration is complete; monitoring remains

### Details

Backfill is done and canary is healthy
```

Notes:

- The heading uses the resolved source session key when available, otherwise the bare session id.
- The current implementation does not include the handoff timestamp in this block.

### 8.3 Nightly snapshot

The nightly job rewrites the snapshot block in `MEMORY.md`.

Snapshot generation is LLM-assisted, but pre-filtering happens in code first. The model is given:

- the current generated block
- active entries
- open items
- stale subjects
- durable entries
- subject-activity summaries
- aggregate signal summaries

Typical snapshot sections are:

- `## Snapshot`
- `## Human Interests`
- `## Current Projects`
- `## Conversation Focus`
- `## Active Tasks`
- `## Open Questions`
- `## Recent Decisions`
- `## Stale Threads`
- `## Durable Memory`
- `## Risks or Watchouts`

Empty sections may be omitted. The generated block is capped to `briefing.maxLines` lines, default 120.

The current pre-filtering behavior is heuristic rather than exhaustive:

- recent active entries are ranked, with handoffs excluded from the active-entry bucket
- open items are ranked with recency, usage, and subject-activity signals
- stale subjects surface older but still significant threads
- durable entries surface older `fact` / `decision` items with positive usage score

This snapshot is intentionally curated rather than exhaustive. It is not required to carry every historical open item forever.

## 9. Memory Tools

Reclaw registers wrapped versions of the builtin `memory_search` and `memory_get` tools under the same tool names.

### 9.1 `memory_search`

Parameters:

| Parameter | Meaning |
|---|---|
| `query` | Keyword or natural-language query |
| `maxResults` | Passed through to the builtin markdown-search leg |
| `minScore` | Passed through to the builtin markdown-search leg |
| `type` | Optional event-type filter |
| `subject` | Optional subject slug filter |
| `status` | Optional task-status filter |

Execution model:

1. If `type`, `subject`, or `status` is present, run a direct structured query over `log.jsonl`
2. If `query` is present, run direct keyword search over log `content` / `detail`
3. If `query` is present and builtin `memory_search` exists, also run builtin semantic/keyword search over indexed markdown memory content
4. Merge the results and render log-backed matches with inline event ids

Example log-backed output:

```text
[id=a3k9x_BmQ2yT] [decision] auth-migration - Queue-based retries for webhook delivery instead of synchronous retries (2026-02-20T14:20:00.000Z)
```

Contracts:

- The log leg is structured + keyword only. There is no vector index over `log.jsonl`.
- `memorySearchCount` is incremented for log-backed result ids returned by the search.
- Semantic search is delegated to the builtin runtime helper and therefore follows OpenClaw's markdown indexing behavior across `MEMORY.md` and generated subject projection files.

### 9.2 `memory_get`

Parameters:

| Parameter | Meaning |
|---|---|
| `path` | File path, event id, or `session:<sessionId>` |
| `from` | Optional line offset for file reads |
| `lines` | Optional line count for file reads |

Execution model:

- File path such as `MEMORY.md`: delegate to builtin `memory_get`
- 12-character event id: return the full JSON log entry and increment `memoryGetCount`
- `subject:<slug>`: return that subject's chronological event chain as a stable lookup handle for an evolving memory thread
- `session:<sessionId>`: resolve the transcript for the current tool context's agent/session namespace and return formatted user/assistant messages

Example event-id response:

```json
{
  "timestamp": "2026-02-20T14:20:00.000Z",
  "id": "a3k9x_BmQ2yT",
  "type": "decision",
  "subject": "auth-migration",
  "content": "Queue-based retries for webhook delivery instead of synchronous retries",
  "detail": "Synchronous retries amplified failures during the outage",
  "session": "abc12345"
}
```

## 10. CLI Contract

### 10.1 Setup and lifecycle

`openclaw reclaw init` performs these tasks:

1. Creates `log.jsonl`, `subjects.json`, and `state.json`
2. Sets `plugins.slots.memory = "reclaw"`
3. Adds `reclaw` to `plugins.allow`
4. Disables `agents.defaults.compaction.memoryFlush`
5. Sets session-retention config to preserve transcripts for provenance and compaction delta extraction:
   - `session.maintenance.pruneAfter = "36500d"`
   - `session.maintenance.maxEntries = 100000`
   - `session.maintenance.resetArchiveRetention = false`
6. Disables the bundled `session-memory` hook
7. Ensures the snapshot and handoff markers exist in `MEMORY.md`
8. Registers or updates the nightly snapshot cron job
9. Fires a post-init system event instructing the main session to update `AGENTS.md` and `MEMORY.md` guidance blocks

Important: `init` does not directly rewrite `AGENTS.md` or inject the `RECLAW MEMORY NOTICE` block into `MEMORY.md`. That is delegated to the post-init guidance flow.

`openclaw reclaw uninstall`:

- removes the config changes above
- removes the snapshot cron job
- removes the generated snapshot block from `MEMORY.md`
- preserves log data

It does not fully scrub all handoff or guidance content from the workspace.

`openclaw reclaw verify` checks:

- store files exist and are parseable
- `openclaw.json` contains the expected slot, session-retention, hook, and memory-flush settings
- `AGENTS.md` contains Reclaw guidance markers
- `MEMORY.md` contains snapshot markers, handoff markers, and the Reclaw notice block
- the nightly snapshot cron job exists and is enabled

### 10.2 Operational commands

Primary CLI groups:

- `openclaw reclaw log`
- `openclaw reclaw search`
- `openclaw reclaw trace`
- `openclaw reclaw status`
- `openclaw reclaw subjects list|add|rename`
- `openclaw reclaw projection refresh|generate|list`
- `openclaw reclaw snapshot refresh|generate|list|status`
- `openclaw reclaw handoff refresh|list|status`
- `openclaw reclaw import ...`

Notes:

- `projection generate` is an alias for `projection refresh`
- `snapshot generate` is an alias for `snapshot refresh`
- the nightly cron uses `snapshot refresh`
- `trace` groups event history by subject and renders chronological chains

## 11. Import Contract

Reclaw can import historical conversation data from:

- ChatGPT exports
- Claude exports
- Grok exports
- existing OpenClaw memory/transcript data

### 11.1 Import model

- Imports are async by default and run through queued cron-backed worker jobs
- `--dry-run` previews selection and extraction without writing
- Import selection is deduped by `<platform>:<conversationId>`
- Selected conversations are processed oldest-to-newest by `updatedAt`
- Imported conversations are recorded in `state.json.importedConversations`
- `--force` bypasses imported-conversation dedupe

### 11.2 Import extraction

Historical import uses the same general extraction model with historical-mode guidance:

- only durable future-useful information should be kept
- handoff entries are dropped
- per-entry timestamps may be preserved when valid
- invalid or missing timestamps fall back to the conversation `updatedAt`

Imported session ids use:

```text
reclaw:<platform>:<conversationId>
```

When transcript writing is enabled, Reclaw also writes OpenClaw transcript sessions and registers them in `sessions.json`.

After a successful non-dry-run import run, Reclaw refreshes the full subject projection set so imported memories become available to builtin markdown semantic search without requiring a separate manual rebuild.

### 11.3 Import job state

Async import jobs track:

- status: `queued`, `running`, `completed`, `failed`
- source platform and file path
- requested options
- attempts
- progress counters
- final summary
- cron job metadata for the queued worker

Supported operational commands:

- `openclaw reclaw import status [jobId]`
- `openclaw reclaw import resume [jobId]`
- `openclaw reclaw import stop [jobId]`
- `openclaw reclaw import run --job <id>`

## 12. Package Shape

The codebase should remain organized around these responsibilities:

- `packages/plugin`
  - plugin entrypoint and registration
  - prompt files used by extraction, snapshot generation, and workspace guidance
  - extraction hooks and pipeline
  - memory-tool wrappers
  - log schema and query helpers
  - subject registry management
  - subject markdown projection rendering and refresh helpers
  - subject matching helpers for extraction context
  - `MEMORY.md` managed-block writers
  - state persistence and normalization
  - import adapters, extraction, and job orchestration
  - CLI commands for setup, recall, projections, snapshotting, subjects, and import
- `packages/skill`
  - an agent-facing skill that explains how to use Reclaw in conversation

## 13. Out of Scope

The current implementation does not include:

- daily memory-note files
- a vector index over `log.jsonl`
- Obsidian sync or note generation
- bidirectional reconciliation with external notes
- concurrent operation with `memory-core`

## 14. Acceptance Checklist

A similar implementation should satisfy these checks:

1. `init` creates the store, updates OpenClaw config, ensures markers, and registers the nightly cron
2. Live sessions produce structured log entries and update the latest handoff block when a handoff is emitted
3. Live extraction enforces exactly one final handoff, with a repair pass when needed
4. Startup sweep can extract missed sessions and retry failed ones
5. Compaction-triggered delta extraction records compaction state and only processes transcript content newer than the last extraction watermark
6. Snapshot generation rewrites only the snapshot block and preserves unrelated `MEMORY.md` content
7. `memory_search` returns log-backed results with inline ids and combines them with builtin markdown semantic results when queried
8. `memory_get` can read files, log entries by id, subject histories by `subject:<slug>`, and transcripts by `session:<id>`
9. Extraction context can match subjects from transcript text beyond exact kebab-case slug mentions
10. Subject projection files are generated under `reclaw-memory/subjects/` and preserve event ids in markdown
11. Successful live extraction refreshes touched subject projections, and successful non-dry-run import refreshes the projection set
12. Subject add/rename flows update the registry, and rename also rewrites historical log subjects
13. Async import jobs can be queued, inspected, resumed, stopped, and executed by worker runs
14. Verify checks the fully initialized workspace, including guidance markers, memory notice markers, and the projection directory
